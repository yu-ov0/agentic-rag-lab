# agentic-rag-lab

一个**多跳 Agentic RAG** 实验：把复合问题拆成子问题，逐个检索、判断证据是否充分，
不足则改写重试，仍不足则拒答；并与「整句一次检索」的固定管线在同一套检索器上对比。

结论先放这里：**证据召回 0.167 → 0.667，且正好等于单跳检索的上限 0.667**——
提升全部来自分解，循环本身没有损失；剩下的 4 条失败是单跳召回不够深，不是 Agent 的问题。

语料复用 [med-rag-lab](https://github.com/yu-ov0/med-rag-lab) 的 833 个可引用 chunk
（中国高血压防治指南 2024 + 中国 2 型糖尿病防治指南 2020），检索器也是同一套
BM25 + BGE-small-zh + RRF + bge-reranker-v2-m3。所有指标可复现。

## 0. 快速开始

```bash
uv sync
bash scripts/download_models.sh        # 模型不入库

# 评测集由 26 道单跳题两两组合而来（固定配对，可复现）
python eval/build_multihop.py

python eval/run_eval.py                # baseline vs agentic，约 3 分钟（CPU）
python eval/eval_rewrite.py            # 改写重试的真实恢复率

uvicorn api.app:app --app-dir src --port 8000
curl -s localhost:8000/ask -H 'content-type: application/json' \
  -d '{"question":"诊室血压诊断高血压的界值是多少？糖尿病的诊断标准是什么？"}'
```

`/ask` 返回答案、引用，以及完整 trace：拆出了哪些子问题、每次检索的分数、
是否改写、是否拒答。

## 1. 要解决的问题

固定管线（一个 query → top-k → 生成）在多跳问题上有两个具体失效模式：

1. **注意力被稀释**：一个问题里有两个主题，向量/BM25 只能匹配到其中一个，
   另一个主题的 gold 被挤出 top-k。实测 baseline 平均只找到 0.83/2 个 gold。
2. **无法判断"够了没有"**：检索永远返回 top-k，哪怕全是噪声，生成层也照单全收。

对应两个动作：**分解**（让每个子问题有自己的检索）和**充分性判断**（用重排分数决定
继续、改写还是拒答）。

## 2. 循环设计

```
question
   │ decompose（规则：按问句边界切，保留问号）
   ▼
sub-question ──► 检索 top-5 ──► 重排 top-1 ≥ 2.0 ?
   │                                   │ 否，且还有重试次数
   │                                   ▼
   │                                改写 ──► 再检索
   ▼
合并证据（按 chunk_id 去重，按分数排序，上限 10）──► 带引用的答案
                                              └──► 一条都不充分 → 拒答
```

三个刻意的选择：

- **分解不用 LLM**：规则可断言、零延迟、可在 CI 里测。代价是"一句话藏两个跳"的
  问法拆不开（见 §7）。
- **保留问号**：子问题与原来的单跳题逐字一致，多跳指标才能和单跳上限直接比较。
  实测去掉"？"会让 h08 的 gold 从 rank 1 掉到 rank 3——中文 BM25 里标点也是 token。
- **充分性用重排分，不用向量相似度**：重排是 (query, chunk) 的直接相关性判断，
  阈值沿用 med-rag-lab 的校准（可答最低 2.361 / 语料外最高 1.532 → 取 2.0）。

## 3. 评测集

`eval/eval_set.jsonl`，12 条，由 `eval/single_hop.jsonl` 的 26 道人工标注题
两两组合（`eval/build_multihop.py` 里写死配对，可复现）：

- **6 条跨文档**（高血压 + 糖尿病），考的是"两个主题互相抢召回"；
- **6 条同文档**（同一指南内两个不同段落），更难：词表重合、主题相近。

每条的 gold 是两个不同 chunk（脚本里有断言），避免"一段话同时答两问"的假多跳。

## 4. 结果

同一套检索器（候选池 10、重排），12 条多跳题，CPU：

| 配置 | 证据召回（双 gold 全中） | gold 命中率 | 证据块数 | 检索次数 | 延迟 p50 |
|---|---|---|---|---|---|
| baseline：整句 top-5 | 0.167 | 0.417 | 5 | 1 | 2.80 s |
| agentic：同预算 5 块 | 0.333 | 0.625 | 5 | 2 | 5.54 s |
| **agentic：每跳 top-5（≤10 块）** | **0.667** | **0.833** | 9.8 | 2 | 5.54 s |
| 单跳上限（每跳单独检索 top-5） | 0.667 | — | — | — | — |

分类型：

| 类型 | baseline | agentic |
|---|---|---|
| 跨文档（6） | 0.000 | 0.667 |
| 同文档（6） | 0.333 | 0.667 |

拒答：10 条语料外问题（肺癌、抑郁症、阑尾炎等）**10/10 拒答**，
最高 top-1 重排分 1.532 < 阈值 2.0，与校准一致。

## 5. 分析：提升来自哪里

**agentic 的 0.667 与单跳上限 0.667 完全相等**，说明循环没有引入损失：
凡是「每一跳单独检索时能找到 gold」的题，分解后都找到了。

剩下 4 条失败（mh05/mh06/mh09/mh10）都有一跳的 gold 在它自己的 top-5 之外：

| 子问题 | gold 在单跳 top-10 里的名次 |
|---|---|
| d12 何时用 SGLT2i/GLP-1RA | 7 |
| h13 合并糖尿病降压目标 | 8 |
| h10 白大衣性高血压定义 | 9 |
| d07 GLP-1RA 作用 | 未进 top-10 |

26 道单跳题里只有 20 道能把 gold 排进 top-5。**所以多跳的下一步不是加循环，
而是把单跳召回做深**（更大候选池、更好的重排、或按章节先路由再检索）。
这一点如果不测"上限"，很容易误判成"Agent 还不够聪明"。

**代价是明确的**：证据块 5 → 9.8，检索 1 → 2 次，延迟 2.80 → 5.54 s。
同预算 5 块时只有 0.333——因为每跳的 gold 常排在它自己的第 4-5 位，
5 块预算分给两跳就切掉了。**提升依赖证据预算，这一点不能藏着说。**

## 6. 改写重试：一个负面结果

多跳集上改写触发 0 次（子问题都是指南原句，分数都够）。于是单独做了一组
口语化提问（`eval/colloquial.jsonl`，10 条，"血压多少算高？"这种）：

| | 过阈值（可答） | gold 进 top-5 |
|---|---|---|
| 原问法 | 4/10 | 0.2 |
| 去疑问词改写 | 5/10 | 0.2 |
| 去疑问词 + "临床指南 推荐" | 5/10 | 0.1 |

改写恢复了 2 条（c06 低血糖分级、c10 二甲双胍），但**误伤 1 条**（c09 联合降压，
2.62 → 1.71），gold 命中反而下降。结论：**盲改写不可靠，只能当兜底**；
真要解决口语化查询，得做术语映射（"血压高" → "高血压 诊断标准"）或
伪相关反馈，而不是往 query 后面堆词。这条我没有继续做，所以也没写成"有效"。

## 7. 已知限制

- 分解是规则：一句话里藏两个跳（"A 和 B 分别是什么？"）拆不开，指代型追问
  （"那它的剂量呢？"）也不支持；
- 阈值 2.0 沿用 med-rag-lab 在 26 道单跳题上的校准，而本项目的多跳题由这些题
  组合而来，拒答指标有轻微乐观偏差；
- 证据合并按分数取前 10，没有做上下文压缩；真实产品到 10 块就该上压缩或摘要；
- 两个子问题串行检索，没有并行；CPU 上 5.5 s 的延迟主要花在两次重排；
- 答案是抽取式拼接（不调 LLM），所以评的是检索而不是生成质量；
- 12 条多跳题样本很小，0.167 vs 0.667 的置信区间很宽，结论只对本数据集成立。

## 8. 目录

```
src/rag/        BM25 / 向量 / RRF / 重排（与 med-rag-lab 同源）
src/agent/      decompose（规则分解）/ sufficiency（阈值+改写）/ agent（循环）/ answer（引用）
src/api/        FastAPI /ask，返回答案 + trace
eval/           12 条多跳集、10 条口语化集、10 条语料外集、评测脚本、结果 JSON
tests/          12 个单测，用 stub retriever，CI 不需要模型
```

`tests/` 里所有用例都注入 stub retriever：CI 只装依赖、不下载 1.1 GB 模型，
所以测试跑 0.2 秒，也不会因为模型下载失败而红。
